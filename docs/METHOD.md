# 可复用的研究流程

这是一份方法说明，不提供原游戏输入准备、解保护、专有模块转换或完整移植构建命令。

## 1. 定义范围和可重复输入

先记录目标版本、平台、工具链和输入来源。输入核验、哈希与派生材料保留在本地；不要把完整清单、游戏片段或私有路径放进公开报告。未知来源的输入不作为基线。

将研究目标拆成“配置成功”“程序启动”“菜单显示”“战场可交互”“整局完成”“长时间稳定”。各阶段有不同证据，不能用前一阶段替代后一阶段。

## 2. 先建立容易比较的基线

优先选择行为更容易对照的宿主环境验证调用约定、状态传递、导入接口和异常控制流。先做小规模合成程序与接口测试，再处理真实输入。平台迁移时保持版本一致，避免同时更换输入、翻译器和渲染后端。

## 3. 明确语义边界

把地址空间、CPU 状态、调用约定和系统接口作为显式契约。每次修改指令语义、内存行为或线程状态，都针对受影响路径比较输入/输出、寄存器、标志和写入范围。真实程序差分使用的字节与数据留在本地；公开测试只用自写合成输入。

## 4. 从小图形探针走向复杂场景

依次验证窗口和 surface、简单绘制、资源更新、输入映射及实际场景。像素读回和窗口实际显示是两种证据；读回正确但窗口黑屏时，要检查呈现与 UI 线程边界。图形能力按实际支持报告，验证层告警保留到问题解决，不能靠关闭诊断宣称修复。

## 5. 逐平台处理生命周期

移动端额外关注后台/前台、surface 重建、音频设备和触摸取消。Apple 关注 UI 线程、平台权限和 GPU 异步资源寿命。Windows 上成立的指针、对齐或内存序假设不能直接搬到 ARM64。

## 6. 性能由测量决定

先区分启动、加载、CPU 执行、锁竞争、图形提交与 GPU 时间，再定位热点。可能有价值的方向包括减少重复状态寻址、避免无效唤醒、控制间接调用成本和减少无用循环检查；是否有效依赖实际测量。

对照记录必须包含版本、构建配置、缓存状态、诊断开关和场景。同一轮改变缓存与校验层等多个变量，只能说明结果变化，不能确定原因。报告帧时间分布而不是只看平均 FPS。

## 7. 验证到什么程度，就报告到什么程度

| 改动 | 主要验证 |
| --- | --- |
| 指令、寄存器、栈、控制流 | 针对性语义差分或等价性验证 |
| 原子操作、锁、线程状态 | 并发隔离、递归、唤醒及内存行为检查 |
| 图形资源寿命 | 最小 GPU 探针、验证层与真机场景 |
| 窗口和输入 | 实际显示、黑边/缩放边界、按下/释放配对 |
| 配置与组织 | 配置产物、路径与失败条件检查 |
| 公开内容 | 来源审查、精确文件清单、索引与历史扫描 |

通过相关验证后推进下一阶段；出现新差异再扩大检查。公开工具通过测试仅说明这些工具的行为，不代表未公开系统的正确性。
